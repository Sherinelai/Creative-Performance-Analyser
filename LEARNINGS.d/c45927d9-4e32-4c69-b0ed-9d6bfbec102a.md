## 2026-07-27 — c45927d9-4e32-4c69-b0ed-9d6bfbec102a

- **Shift (most reusable thing built):** a **three-layer test ladder**, because each layer is blind to
  the next. `tools/dump_sql.js` proves the SQL *builds* (loads `Code.js` in a `vm` with Apps Script
  stubbed); `tools/run_pipeline.js` runs `fetchCreativeData` end-to-end against pre-fetched rows, so
  `mergeAllData` / `analyzeCreativePerformance` / the classification run outside GAS;
  `tools/render_smoke_test.js [--real]` drives the client under a Proxy DOM stub, on demo fixtures or
  on a real server response. `node --check` proves only that the file parses. **And when every layer
  passes, force the suspect input** — setting `perf = []` reproduced "all the numbers are gone"
  exactly, which no amount of code-reading had.
- **Finding (bit twice, in different clothes):** **swallowing a failure into `[]` is how a dashboard
  lies.** `runSQLParallel` degrades any failed query to an empty array. (a) The one query carrying
  every number timed out → the page rendered *complete but empty* (totalSpend 0, null rates, 141
  creatives still listed from the inventory path). (b) The config query had **two** stale columns —
  `apps.bundle_id` (dropped upstream; it was being selected AS app_name, so `display_name` replaces
  it) and `campaigns.campaign_type` (the table has `campaign_type_id`; the name lives in
  `campaign_types`) — so it had been failing for **every** campaign, silently, costing the real app
  name. Nothing surfaced either until a harness ran the pipeline outside GAS. Fixes now: perf gets its
  own uncontended wave plus a retry, and an empty perf with non-empty inventory **returns an error
  instead of drawing zeros**.
- **Finding:** *a filter should change what you SEE, not what things MEASURE.* Filtering the creative
  table rebuilt every format group from the filtered subset, so a format's spend, weighted
  ROAS/RPI/RPA and counts moved as soon as you narrowed the view. Groups now aggregate over all
  creatives and a `visibleCids` set gates the sub-rows. Corollary: when a row's numbers cover more
  than it lists, **say so** — hence the "(N of M shown)" hint, or it reads as a mismatch.
- **Shift (my own bad trade, reverted):** merging all 13 queries into one parallel batch saved ~28s of
  a ~68s load but made the slowest, least predictable query lose the race — `perf` measured **40s, 94s
  and once >120s (hard timeout) on the same campaign within a day.** **Parallelism that makes the
  critical path less reliable is not an optimization.** Measure the critical path's *variance*, not
  just its mean.
- **Shift (second hypothesis killed by measurement, also reverted):** I rewrote the perf query
  "aggregate first, join second" — group the fact table by `creative_id`, join the dimension tables to
  the ~250-row result instead of to millions of fact rows. It came out **227s with `arbitrary()` and
  345s with `MAX()`**, against 40–94s for the original wide `GROUP BY` that joins first. **String
  aggregates over millions of rows cost more than putting those columns in the group key** — Trino
  parallelises a wide hash group-by better than few groups with varchar accumulators. Reverted to the
  original (verified byte-identical SQL). Two general lessons: revert on measurement rather than
  shipping a plausible rewrite, and **the scan is the floor** — 73853 has 4,029,065 rows in a 30-day
  window, `GROUP BY creative_id` + 6 sums alone is 32s, the full query 86s, and UrlFetchApp gives up
  first. No SQL rewrite recovers that; only a mechanism change (cache, async second call, shorter
  window) will. Also disproved on the way: **partition pruning was not the problem** even though `dt`
  *is* a partition column (Trino refuses a query without a `dt` filter) — function-wrapped 36s vs
  DATE_FORMAT string comparison 52s, identical row counts, so the "string comparison for pruning"
  comment elsewhere in the codebase does not generalise.
- **Finding:** *an error message that tells the user to do X must make X possible.* Mine said "shorten
  the lookback window" while the UI only offered 30/60/90 days. Added 7 and 14 — on 73853 that is 19s
  and 46s versus 86s, which is the difference between working and not.
- **Shift (the through-line):** every other real bug was **the same fact derived twice**, surfacing
  only when two consumers disagreed on screen: MCO rules in 4 places, the format mapping in 4, metric
  direction in 4, performance classes in 2, the primary metric in 3, "which creatives are paused" in
  2. Fix shape: the fact as data in one object (`MCO_RULES`, `METRICS`, `FORMAT_DEVICE`), prose
  compiled from one `.md`, one classifier, one resolver, `getConfig()` as the single channel to the
  client, and `tools/check_single_source.py` to keep it true. **Compute once, stamp it on the row.**
  Corollary that bit hardest: **a count in a badge must come from the same rows as the count beside
  it** — the "N paused" badge was a pauseLog row count carrying a `HAVING revenue > $1` filter
  measured in a *different revenue table*; 41535 showed tile 36 vs badge 7. An enrichment query must
  never decide membership. **Still open, same shape:** the Video/Interactive donuts are drawn by
  `aggregateBreakdown()` from `creativePerf` with the format table's exact weighting (so chart and
  table reconcile by construction), but the prose underneath them — `localVideoSummary(tb)` /
  `localInteractiveSummary(tb)` and the AI payload — reads `R.typeBreakdown`, a *separate* query with
  its own window. A chart and its caption disagreeing is the badge bug again; fix is to feed both from
  `aggregateBreakdown()`.
- **Finding (domain, verified not assumed):** device targeting comes from
  `pinpoint.public.campaigns_targeted_devices` (>1 row = All, ids 3/5 = Tablet). It matters because
  **a format a campaign cannot serve is not a gap** — a phone-only campaign was being shown five
  empty Tablet rows reading as "you're missing these", and the AI was free to recommend tablet
  creatives. Native/MRECT are phone formats: of all enabled creatives in those formats, 49.6% sit on
  Phone campaigns, 50.0% on All, only **0.4%** on Tablet-only. Safe to classify strictly because the
  map only decides which **empty** rows to seed — a format with actual creatives always gets a row.
- **Finding (debugging technique):** when a *visual* breaks, **diff the render path against the
  deployed known-good version before reading code** (`clasp pull --versionNumber N`). The donut's
  geometry was byte-identical to v130, pointing straight at the data shape I had introduced —
  metric-less rows entering the spend series with value 0, adding 0% legend rows and shifting every
  colour slot.
- **Finding:** *a state meaning "not serving" is invisible to any activity-driven query*, twice.
  `queuing` (`current_status='excluded'`) has no rows in `analytics.daily_attr_event_d7`, and both the
  perf query and the misleadingly-named *inventory* query are driven by it — 41535 displayed 3 of 16.
  And **detaching a creative does not pause it**: all three detached creatives on 64417 are still
  `'enabled'`, so they counted as Active and appeared nowhere as a change. Both now surface
  (metric-less rows; a DETACHED tag that deliberately changes no count).
- **Finding (SQL, with a counter-example):** push the filter **inside** the CTE — the supplied
  unassigned-creatives query filtered only in the outer WHERE, leaving the CTE to aggregate the whole
  `elephant_changes` audit table (120s timeout → ~18s once filtered inside on the raw JSON string, no
  CAST). But the same instinct was **wrong** for the perf query's unscoped CTEs: 1,581,908 rows cost
  6.3s vs 5.0s scoped. Supplied Looker SQL is also usually over-joined: dropping the
  `analytics.trimmed_daily` join from the device query lost nothing and saved time. There is a **~4–5s
  floor per query** regardless of size. And `pinpoint.public.creatives.inventory_format` is a Postgres
  enum (`mab_inventory_format`) — `LIKE` fails until you `CAST(... AS VARCHAR)`.
- **Finding:** *test a campaign of a different shape or you never run the branch.* 41535/77022 were
  ROAS; the CPA branch held a label bug. On 78934 `campaign_type` is `'brand'`, so
  `detectTypeFromName` guesses from the campaign NAME and defaults to `ua_cpr` while `goal_2='rpa'`.
  `resolvePrimaryMetric_` now decides once: optimization_state and goals first, campaign type last.
- **Shift (hard-won):** v132 shipped `R._metricLabel(...)` from a blind `str.replace` that matched
