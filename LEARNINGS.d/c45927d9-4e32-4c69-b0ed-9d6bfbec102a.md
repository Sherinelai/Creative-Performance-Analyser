## 2026-07-27 — c45927d9-4e32-4c69-b0ed-9d6bfbec102a

- **Shift (most reusable thing built):** a **three-layer test ladder** for this app, because each
  layer is blind to the next. `tools/dump_sql.js` proves the SQL *builds* (loads `Code.js` in a `vm`
  with Apps Script stubbed); `tools/run_pipeline.js` runs `fetchCreativeData` end-to-end against
  pre-fetched rows, so `mergeAllData` / `analyzeCreativePerformance` / the classification are
  executable outside GAS; `tools/render_smoke_test.js [--real]` drives the client under a Proxy DOM
  stub, either on demo fixtures or on a real server response. `node --check` proves only that the
  file parses. **And when all layers pass, force the suspect input** — setting `perf = []` reproduced
  "all the numbers are gone" exactly, which no amount of code-reading had.
- **Finding:** **swallowing a failure into `[]` is how a dashboard lies.** `runSQLParallel` degrades
  any failed query to an empty array, so when the one query that carries every number (spend,
  revenue, ROAS, RPI, RPA, CIs) timed out, the page rendered *complete but empty*: totalSpend 0,
  null rates, 141 creatives still listed from the inventory path. A missing critical input must
  produce an error, never a plausible-looking zero. Same lesson in a different key: the config query
  has been failing for **every** campaign for who knows how long (`apps.bundle_id` was dropped
  upstream — "Column 'apps.bundle_id' cannot be resolved"), silently costing the app name and the
  KPI target, and nothing surfaced it until a harness ran the pipeline outside GAS.
- **Shift (my own bad trade, reverted):** merging all 13 queries into one parallel batch saved ~28s
  of a ~68s load, but made the slowest, least predictable query compete for the connection and lose.
  `perf` measured **40s, 94s and once >120s (hard read timeout) on the same campaign within one
  day.** It now runs in its own uncontended wave with one retry, and the other twelve follow in
  parallel. **Parallelism that makes the critical path less reliable is not an optimization** —
  correctness first, and measure the critical path's variance, not just its mean.
- **Shift (the through-line):** every other real bug this session was **the same fact derived
  twice**, surfacing only when two consumers disagreed on screen. MCO rules in 4 places, the format
  mapping in 4, metric direction in 4, performance classes in 2, the primary metric in 3, "which
  creatives are paused" in 2. Fix shape: the fact as data in one object (`MCO_RULES`, `METRICS`),
  prose compiled from one `.md`, one classifier, one resolver, `getConfig()` as the single channel to
  the client, and `tools/check_single_source.py` to keep it true. **Compute once, stamp it on the
  row.** Corollary that bit hardest: **a count in a badge must come from the same rows as the count
  beside it** — the "N paused" badge was a pauseLog row count carrying a `HAVING revenue > $1` filter
  measured in a *different revenue table*; campaign 41535 showed tile 36 vs badge 7. An enrichment
  query must never decide membership.
- **Finding (debugging technique):** when a *visual* breaks, **diff the render path against the
  deployed known-good version before reading code** (`clasp pull --versionNumber N`). The donut's
  geometry was byte-identical to v130, which pointed straight at the data shape I had introduced —
  metric-less rows entering the spend series with value 0, adding 0% legend rows and shifting every
  colour slot.
- **Finding:** *a state meaning "not serving" is invisible to any activity-driven query*, twice.
  `queuing` (`current_status='excluded'`) has no rows in `analytics.daily_attr_event_d7`, and both
  the perf query and the misleadingly-named *inventory* query are driven by it — 41535 displayed 3 of
  16. And **detaching a creative does not pause it**: all three detached creatives on 64417 are still
  `'enabled'`, so they counted as Active and appeared nowhere as a change. Both now surface (metric-less
  rows; a DETACHED tag that deliberately changes no count).
- **Finding (SQL perf, with a counter-example):** push the filter **inside** the CTE — the supplied
  unassigned-creatives query filtered only in the outer WHERE, leaving the CTE to aggregate the whole
  `elephant_changes` audit table (120s timeout → ~18s once filtered inside on the raw JSON string, no
  CAST). But the same instinct was **wrong** for the perf query's unscoped CTEs: 1,581,908 rows cost
  6.3s vs 5.0s scoped. Measure before optimising; there is also a **~4–5s floor per query** (SQL
  Runner round trip + Trino planning).
- **Finding:** *test a campaign of a different shape or you never run the branch.* 41535/77022 were
  ROAS; the CPA branch held a label bug. On 78934 `campaign_type` is `'brand'`, so
  `detectTypeFromName` guesses from the campaign NAME and defaults to `ua_cpr` while `goal_2='rpa'`.
  `resolvePrimaryMetric_` now decides once: optimization_state and goals first, campaign type last.
- **Shift (hard-won):** v132 shipped `R._metricLabel(...)` from a blind `str.replace` that matched
  **mid-identifier** (`isCpa?'RPA':'ROAS')` inside `R._isCpa?…`). Valid syntax; at runtime a
  mid-render throw leaves the rest of the DOM unwritten, so the page died after the campaign summary.
  Never blind-replace in a minified line; print the result. Keep fixtures for every new data shape —
  metric-less and detached rows now live in the demo data for exactly that reason.
- **Shift:** on a production regression, **roll back first, diagnose second.** `clasp redeploy
  <deploymentId> [-V n]` updates the existing deployment and **keeps the /exec URL**;
  `create-deployment` mints a new URL and leaves production on the old code. Production is
  version-pinned, so `clasp push -f` alone is safe — the separate `@HEAD` deployment is where the
  user verifies before promoting.
- **Finding:** *creative state is READ, not derived* (three mutually exclusive states from the queue
  PDT; the 25K/7-day rule only says when the platform flips `is_currently_optimizing`). Related
  smell: **collapsing a mutually-exclusive enum into "one value + a boolean"** — the double-count is
  automatic once two consumers read different halves. And the code twice assumed 2 states where the
  source has more (`campaigns.state`: enabled/paused/hidden/deleted; `creatives.state`:
  enabled/paused/deleted, which is why Active+Paused ≠ Total): **query the state distribution first.**
- **Finding:** Trino rejects `ORDER BY` expressions absent from a `SELECT DISTINCT` select list.
  Dated Looker PDTs need a *verified* resolver (`resolvePDT_` proves the columns exist via
  `SHOW COLUMNS` — for the queue PDT those columns *are* the state definition). `runHealthCheck()`
  (14 checks) is the pre-deploy gate and how the user confirms Script Properties.
- **Shift:** model-id bumps are not string swaps. On `claude-sonnet-5` adaptive thinking is **on when
  `thinking` is omitted** and `max_tokens` caps thinking + response *together*; the inherited
  `max_tokens: 1024` would have truncated the JSON into a generic "unavailable".
