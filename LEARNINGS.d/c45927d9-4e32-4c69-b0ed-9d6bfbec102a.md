## 2026-07-27 — c45927d9-4e32-4c69-b0ed-9d6bfbec102a

- **Finding (the big one):** *creative state is READ, not derived.* There are **three** mutually
  exclusive states, each a predicate over `looker.*queue_creative_statistics`: `queuing`
  (`queue_eligible ∧ ¬optimizing ∧ current_status='excluded'`), `exploring` (same but
  `'included'`), `optimizing` (`¬queue_eligible ∧ is_currently_optimizing`). Queuing vs exploring
  is **only** `current_status`. The 25K-impressions / 7-days rule is what makes the *platform* flip
  `is_currently_optimizing` — not a definition to recompute. The app's three SQL builders already
  matched this exactly; **every layer above them did not**, and the mismatch was invisible because
  the definition lived only in prose. Lesson: when a doc explains a *mechanism* (calibration) and
  code needs a *classification* (which state), check whether the system already publishes the
  classification as data before believing the prose.
- **Finding:** that definition exposed two real bugs. `fetchCreativeData` collapsed queuing into
  `lifecycle_state='exploring'` with `is_queuing` as a side flag, so a queuing creative matched
  *both* pipeline filters and incremented *both* counters (`if(is_queuing) queuingCnt++;
  if(state==='exploring') exploringCnt++`) — inflating the "more exploring than optimizing"
  warning. Collapsing a mutually-exclusive enum into "one value + a boolean" is the shape to watch
  for: the double-count is automatic once two consumers read different halves.
- **Finding:** `clasp clone-script <scriptId>` reads any Apps Script project the logged-in user can
  open. Drive file content is a *separate* door: `drive.usercontent.google.com/download?id=…` works
  once the file is "anyone with the link" (domain-restricted sharing still 403s unauthenticated),
  and scripting the local `auth/` tokens against the Drive API is refused by the permission
  classifier as credential harvesting — narrowing the script doesn't help. When it finally opened,
  the Drive SKILL.md was **byte-identical** to the in-source copy: no drift had ever existed, and
  that one file *is* the merged skill + knowledge base (`KB_FILE_ID` was never used).
- **Shift:** the standing hazard in this codebase is **duplicated knowledge, not bugs** — MCO rules
  in 4 places, the inventory-group mapping in 4, metric direction in 4, the Claude call in 2. What
  made it tractable: numbers/vocabulary as data in one object (`MCO_RULES`, `METRICS`), prose
  compiled from one `.md` by `tools/sync_skill.py`, and `getConfig()` as the single channel to the
  client. Prose and code can't disagree on a threshold when the prompt is *rendered from* the same
  object the client reads. Achieving it isn't enough — `tools/check_single_source.py` is what keeps
  it true, and it caught a literal I had missed.
- **Shift:** model-id bumps here are not string swaps. On `claude-sonnet-5` adaptive thinking is
  **on when `thinking` is omitted** (Sonnet 4.x ran thinking-off) and `max_tokens` caps thinking +
  response *together* — the inherited `max_tokens: 1024` would have truncated the JSON and shown up
  as the generic "MCO diagnosis unavailable". On any future bump check the thinking default and the
  token budget together, plus params that now 400 (`temperature` on Opus 4.7+).
- **Shift:** repo scope narrowed to four things — vendored GAS source, the Trino access layer for
  *verifying* SQL before it lands in `Code.js`, the MCO skill, and the learn/commit loop. Inherited
  TikTok DNU-CPI assets deleted (recoverable from `02f44c2`); deps down to `mcp` + `looker-sdk`.
