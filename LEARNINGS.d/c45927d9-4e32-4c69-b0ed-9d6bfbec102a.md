## 2026-07-27 — c45927d9-4e32-4c69-b0ed-9d6bfbec102a

- **Finding (best new technique):** to audit a GAS dashboard's numbers, **extract the app's own SQL
  and run it yourself**: `tools/dump_sql.js` loads `Code.js` in a `vm` with Apps Script stubbed and
  the PDT resolvers pinned, so `buildCreativeLevelPerfSQL(41535, 30)` etc. return the exact strings
  the app sends; run those through the `creative-mcp` Trino runner and recompute the derived figures
  in Python. That turns "the numbers look off" into "old logic lists 3 creatives, the table tags 1,
  here are the two extras and why" — verification instead of code-reading.
- **Finding:** *a state that means "not serving" is invisible to any activity-driven query.* 13
  creatives had a pipeline state but weren't in the dashboard at all — **all 13 were `queuing`**
  (`current_status='excluded'` = excluded from serving → no rows in
  `hive.bi.cstudio_analytics_daily_v1`). Both the perf query **and** the one called *inventory* are
  driven by that table over the lookback window — the name lies; it is not a creative registry — so
  a queued creative usually cannot appear in `creativePerf`. Exploring/optimizing are serving, hence
  100% coverage. Campaign 41535: queuing **3 of 16** displayed, exploring 6/6, optimizing 33/33. The
  undercount lands on precisely the state a strategist needs (new creatives stuck waiting).
  `result.lifecycleCounts` now publishes {total, displayed} per state and the recommendation reports
  the true queue size.
- **Finding:** the reported "Recommendations vs Creative Performance by Format don't match" was the
  performance classification implemented **twice** (server for the recommendation, client for the
  tags) with three divergences: only the client applied the exclusivity cascade (so a creative below
  the campaign average but *above* its format average was tagged ↑ Format avg **and** listed as
  confirmed poor), only the server protected sole-active creatives, and the two grouped by different
  keys (raw `inventory_format` vs MCO Inventory Group). Quantified on 41535: 3 recommended vs 1
  tagged. Now `classifyCreativePerformance_()` classifies once and stamps `perf_class`.
- **Finding:** two smaller data truths worth remembering — Query E can return a row with a **NULL
  `creative_id`** (1 of 80 on 41535: no state, zero spend) which inflated Total and broke
  Active+Paused=Total; and `variance` (the gate on every performance class) exists only when a
  creative has a confidence interval — **21 of 79 here**, so ~3/4 can never be tagged. The
  recommendation now states its screening coverage instead of implying it screened everything.
- **Shift (hard-won):** *`node --check` is not a test.* I shipped v132 with `R._metricLabel(...)`,
  produced by a blind `str.replace` on a minified line whose search string matched **mid-identifier**
  (`isCpa?'RPA':'ROAS')` inside `R._isCpa?…`). Syntactically valid, so every check passed; at runtime
  a mid-render throw leaves the remaining DOM unwritten, so the page died after the campaign summary.
  `node tools/render_smoke_test.js` now executes the real render chain under a Proxy DOM stub with
  `CFG` empty (worst case) — reproduced the failure before I trusted it on the fix. Never patch a
  minified line with a blind replace; print the result.
- **Shift:** on a production regression, **roll back first, diagnose second.** Deployment mechanics:
  `clasp redeploy <deploymentId> [-V n]` updates the existing deployment and **keeps the /exec URL**;
  `create-deployment` mints a new URL and leaves production on the old code. Production here is
  version-pinned, so `clasp push -f` alone is safe — only the separate `@HEAD` deployment tracks
  pushes, which makes it the place to have the user verify before redeploying.
- **Finding:** *creative state is READ, not derived* — three mutually exclusive states from the queue
  PDT; the 25K-impressions / 7-days rule only describes when the platform flips
  `is_currently_optimizing`. The app's three SQL builders already matched; the layers above didn't.
  When a doc explains a *mechanism* and code needs a *classification*, check whether the system
  already publishes the classification as data.
- **Finding:** **collapsing a mutually-exclusive enum into "one value + a boolean"** is the shape to
  watch for (`lifecycle_state='exploring'` + `is_queuing`): once two consumers read different halves,
  the double-count is automatic.
- **Finding:** twice now the code assumed 2 states where the source has more — `campaigns.state`
  (enabled/paused/hidden/deleted) and `creatives.state` (enabled/paused/deleted). **Query the state
  distribution before reasoning about a state filter.** Trino also rejects `ORDER BY` expressions
  absent from a `SELECT DISTINCT` select list, so a state-priority sort must be a selected column.
- **Shift:** the standing hazard here is **duplicated knowledge, not bugs** — MCO rules in 4 places,
  the format mapping in 4, metric direction in 4, the performance classes in 2, the Claude call in 2.
  Fix shape: data in one object (`MCO_RULES`, `METRICS`), prose compiled from one `.md`
  (`tools/sync_skill.py`), `getConfig()` as the single channel to the client — and
  `tools/check_single_source.py` to keep it true (it caught a literal I'd missed).
- **Shift:** model-id bumps are not string swaps. On `claude-sonnet-5` adaptive thinking is **on when
  `thinking` is omitted** and `max_tokens` caps thinking + response *together*; the inherited
  `max_tokens: 1024` would have truncated the JSON into a generic "unavailable". Check the thinking
  default and the token budget together, plus params that now 400 (`temperature` on Opus 4.7+).
- **Shift:** dated Looker PDTs need a *verified* resolver — `resolvePDT_()` proves via `SHOW COLUMNS`
  that the columns the app reads exist and fails with the candidate list. For the queue PDT those
  columns *are* the state definition. `runHealthCheck()` (14 checks) is the pre-deploy gate and is
  how the user confirms Script Properties; it went 14/14 green.
