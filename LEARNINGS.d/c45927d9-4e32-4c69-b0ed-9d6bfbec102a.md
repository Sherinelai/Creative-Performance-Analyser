## 2026-07-27 — c45927d9-4e32-4c69-b0ed-9d6bfbec102a

- **Shift (the through-line):** every real bug this session was **the same fact derived twice**, and
  each one only showed up when two consumers disagreed on screen. MCO rules in 4 places, the format
  mapping in 4, metric direction in 4, the performance classes in 2, `isCpa`/primary metric in **3**,
  the Claude call in 2. Fix shape that worked: the fact as data in one object (`MCO_RULES`,
  `METRICS`, `PRIMARY_METRIC_BY_CAMPAIGN_TYPE`), prose compiled from one `.md`
  (`tools/sync_skill.py`), one classifier (`classifyCreativePerformance_`), one resolver
  (`resolvePrimaryMetric_`), `getConfig()` as the single channel to the client — plus
  `tools/check_single_source.py` so it stays true. **Prefer "compute once, stamp it on the row" over
  "compute the same rule in both places".**
- **Finding (audit method that paid off three times):** extract the app's own SQL and run it yourself.
  `tools/dump_sql.js` loads `Code.js` in a `vm` with Apps Script stubbed and the PDTs pinned, so
  `buildCreativeLevelPerfSQL(id, 30)` returns exactly what the app sends; run it through the
  `creative-mcp` Trino runner and recompute the derived figures in Python. That turned "the numbers
  look off" into "old logic lists 3 creatives, the table tags 1, here are the two extras and why".
- **Finding:** *test a campaign of a different shape or you never run the branch.* 41535 and 77022 were
  both ROAS; the CPA branch held a bug. On 78934 `campaign_type` is `'brand'`, so `detectType` returns
  null and `detectTypeFromName` **guesses from the campaign NAME**, defaulting to `ua_cpr` (ROAS) —
  while `goal_2='rpa'` and `optimization_state='cpa'`. I had just replaced `isCpa?'RPA':'ROAS'` with a
  campType-derived label, so the header read "7D ROAS" over RPA numbers. Goals and optimization_state
  state the actual target; campaign type is only a fallback. Same family, pre-existing: the KPI tile's
  `primaryMetric` came from campType too.
- **Finding:** *a state meaning "not serving" is invisible to any activity-driven query.* 13 creatives
  had a pipeline state but weren't in the dashboard — **all 13 `queuing`** (`current_status='excluded'`
  → no rows in `analytics.daily_attr_event_d7`). Both the perf query and the one called *inventory*
  (the name lies — it is not a registry) are driven by that table over the lookback window. 41535:
  queuing **3 of 16** displayed, exploring 6/6, optimizing 33/33. Fixed by appending metric-less rows
  (`is_metricless`, spend/revenue 0, rates null); the codebase's metric cells were already `!= null`
  guarded and fall back to `—`, so the render path needed no changes — verified by putting such a row
  in the demo fixtures so the smoke test covers it.
- **Finding (load time, measured):** per-query timings on 77022 — perf **40.3s**, dailyFmt **28.4s**,
  dailyCr **26.3s**, everything else 4–8s; sum 128.6s, slowest single 40.3s. Three lessons: (a) the
  second `runSQLParallel` batch was a **pure barrier** — every query in it needed only campaignId +
  lookbackDays, so ~28s of a ~68s load was spent waiting for nothing (merged into one batch);
  (b) there is a **~4–5s floor per query** (Looker SQL Runner round trip + Trino planning — a 2-row
  query takes 4.2s), and slug creation is still 13 sequential round trips; (c) my first hypothesis was
  **wrong** — unscoped CTEs are not the bottleneck: aggregating 1,581,908 rows costs 6.3s vs 5.0s
  scoped. Measuring told me where *not* to optimise.
- **Shift (hard-won):** *`node --check` is not a test.* v132 shipped `R._metricLabel(...)` from a blind
  `str.replace` that matched **mid-identifier** (`isCpa?'RPA':'ROAS')` inside `R._isCpa?…`). Valid
  syntax, so every check passed; a mid-render throw leaves the remaining DOM unwritten, so the page
  died after the campaign summary. `node tools/render_smoke_test.js` runs the real chain under a Proxy
  DOM stub with `CFG` empty (worst case) — I reproduced the failure on the broken file before trusting
  it on the fix. Never blind-replace in a minified line; print the result.
- **Shift:** on a production regression, **roll back first, diagnose second.** `clasp redeploy
  <deploymentId> [-V n]` updates the existing deployment and **keeps the /exec URL**;
  `create-deployment` mints a new URL and leaves production on the old code. Production is
  version-pinned, so `clasp push -f` alone is safe — only the separate `@HEAD` deployment tracks
  pushes, which makes it the place to have the user verify before promoting.
- **Finding:** *creative state is READ, not derived* — three mutually exclusive states from the queue
  PDT; the 25K-impressions / 7-days rule only says when the platform flips `is_currently_optimizing`.
  The three SQL builders already matched; the layers above didn't. When a doc explains a *mechanism*
  and code needs a *classification*, check whether the system already publishes the classification.
  Related smell: **collapsing a mutually-exclusive enum into "one value + a boolean"**
  (`lifecycle_state='exploring'` + `is_queuing`) — the double-count is automatic once two consumers
  read different halves.
- **Finding:** twice the code assumed 2 states where the source has more — `campaigns.state`
  (enabled/paused/hidden/deleted) and `creatives.state` (enabled/paused/deleted, which is why
  Active+Paused ≠ Total). **Query the state distribution before reasoning about a state filter.**
  Also: Query E can return a row with a NULL `creative_id`; `variance` (the gate on every performance
  class) exists only with a confidence interval — 21 of 79 on 41535, ~half on 78934 — so the ⚠ Poor
  list only ever screens a fraction, which the recommendation now states.
- **Finding:** Trino rejects `ORDER BY` expressions absent from a `SELECT DISTINCT` select list, so a
  state-priority sort must be a selected column. Dated Looker PDTs need a *verified* resolver
  (`resolvePDT_` proves via `SHOW COLUMNS` that the columns exist) — for the queue PDT those columns
  *are* the state definition. `runHealthCheck()` (14 checks) is the pre-deploy gate and how the user
  confirms Script Properties.
- **Shift:** model-id bumps are not string swaps. On `claude-sonnet-5` adaptive thinking is **on when
  `thinking` is omitted** and `max_tokens` caps thinking + response *together* — the inherited
  `max_tokens: 1024` would have truncated the JSON into a generic "unavailable". Check the thinking
  default and the token budget together, plus params that now 400 (`temperature` on Opus 4.7+).
