- **Shift (most reusable thing built):** a **three-layer test ladder**, because each layer is blind to
  the next. `tools/dump_sql.js` proves the SQL *builds* (loads `Code.js` in a `vm` with Apps Script
  stubbed); `tools/run_pipeline.js` runs `fetchCreativeData` end-to-end against pre-fetched rows, so
  `mergeAllData` / `analyzeCreativePerformance` / the classification run outside GAS;
  `tools/render_smoke_test.js [--real]` drives the client under a Proxy DOM stub, on demo fixtures or
  on a real server response. `node --check` proves only that the file parses. **And when every layer
  passes, force the suspect input** — setting `perf = []` reproduced "all the numbers are gone"
  exactly, which no amount of code-reading had.
- **Finding (bit twice, in different clothes):** **swallowing a failure into `[]` is how a dashboard
  lies.** `runSQLParallel` degrades any failed query to an empty array. (a) The one query carrying
  every number timed out → the page rendered *complete but empty* (totalSpend 0, null rates, 141
  creatives still listed from the inventory path). (b) The config query had **two** stale columns —
  `apps.bundle_id` (dropped upstream; it was being selected AS app_name, so `display_name` replaces
  it) and `campaigns.campaign_type` (the table has `campaign_type_id`; the name lives in
  `campaign_types`) — so it had been failing for **every** campaign, silently, costing the real app
  name. Nothing surfaced either until a harness ran the pipeline outside GAS. Fixes now: perf gets its
  own uncontended wave plus a retry, and an empty perf with non-empty inventory **returns an error
  instead of drawing zeros**.
- **Finding:** *a filter should change what you SEE, not what things MEASURE.* Filtering the creative
  table rebuilt every format group from the filtered subset, so a format's spend, weighted
  ROAS/RPI/RPA and counts moved as soon as you narrowed the view. Groups now aggregate over all
  creatives and a `visibleCids` set gates the sub-rows. Corollary: when a row's numbers cover more
  than it lists, **say so** — hence the "(N of M shown)" hint, or it reads as a mismatch.
- **Shift (my own bad trade, reverted):** merging all 13 queries into one parallel batch saved ~28s of
  a ~68s load but made the slowest, least predictable query lose the race — `perf` measured **40s, 94s
  and once >120s (hard timeout) on the same campaign within a day.** **Parallelism that makes the
  critical path less reliable is not an optimization.** Measure the critical path's *variance*, not
  just its mean.
  **Amended 2026-07-28 — the conclusion held, my explanation of it did not.** I wrote this up as the
  slow query "competing for the connection and losing", and repeated that reasoning in comments and in
  the decision to fire the two client passes sequentially. The `fetchAll` finding below shows Trino
  serves three concurrent heavy queries fine (19.4s wall for all three), so **connection contention
  was almost certainly never the mechanism** — the same `fetchAll` ceiling most likely explains both.
  Keep the practice, distrust the story: a fix that works for a reason you have not measured will be
  cited later as if the reason were established. Say which part was measured and which part is a guess.
- **Shift (second hypothesis killed by measurement, also reverted):** I rewrote the perf query
  "aggregate first, join second" — group the fact table by `creative_id`, join the dimension tables to
  the ~250-row result instead of to millions of fact rows. It came out **227s with `arbitrary()` and
  345s with `MAX()`**, against 40–94s for the original wide `GROUP BY` that joins first. **String
  aggregates over millions of rows cost more than putting those columns in the group key** — Trino
  parallelises a wide hash group-by better than few groups with varchar accumulators. Reverted to the
  original (verified byte-identical SQL). Two general lessons: revert on measurement rather than
  shipping a plausible rewrite, and **the scan is the floor** — 73853 has 4,029,065 rows in a 30-day
  window, `GROUP BY creative_id` + 6 sums alone is 32s, the full query 86s, and UrlFetchApp gives up
  first. No SQL rewrite recovers that; only a mechanism change (cache, async second call, shorter
  window) will. Also disproved on the way: **partition pruning was not the problem** even though `dt`
  *is* a partition column (Trino refuses a query without a `dt` filter) — function-wrapped 36s vs
  DATE_FORMAT string comparison 52s, identical row counts, so the "string comparison for pruning"
  comment elsewhere in the codebase does not generalise.
- **Finding:** *an error message that tells the user to do X must make X possible.* Mine said "shorten
  the lookback window" while the UI only offered 30/60/90 days. Added 7 and 14 — on 73853 that is 19s
  and 46s versus 86s, which is the difference between working and not.
- **Shift (what finally worked — change the mechanism, not the SQL):** **`UrlFetchApp`'s timeout is
  not configurable** — there is no option to pass, and the 6-minute execution budget is irrelevant
  because the *request* dies first. So the only way to buy time for an 86s query is to make each
  request smaller: split the lookback into date chunks, fire them through `fetchAll`, and add them up
  in JS. **Correction to my first claim:** N chunks buy N× the budget at **N× the wall clock**, not
  at the same wall clock — see the fetchAll finding below. Two things make it safe:
  **ratios are not additive**, so the chunk queries also select the raw sums (`PERF_SUM_COLUMNS`) and
  every ratio is recomputed from the totals; and the combine is *verified against Trino*, not
  reasoned about — one `GROUP BY GROUPING SETS ((creative_id, chunk), (creative_id))` query returns
  both the pieces and the whole-window truth, and comparing my JS against the SQL's own values gave a
  worst relative error of **2e-14** across rpi/roas/rpa/iti/roas_ci_margin/rpa_ci_delta with zero
  null mismatches. That trick — *one query that returns both the parts and the total* — is the cheap
  way to test any re-aggregation. Grouping by `creative_id` also collapses the mid-window duplicate
  rows for free.
- **Finding (a platform ceiling I still cannot name, and what to do about that):** three perf chunks
  fired together through **`UrlFetchApp.fetchAll` fail from the second one onward** — 73853 returned
  chunk 0 and lost chunks 1 and 2, twice. It is **not** Trino contention and not the SQL: measured
  from outside Apps Script the same three chunks answer in 14-19s both sequentially *and* all three
  concurrently (19.4s wall, 121/396/172 rows). The shape of the failure — first one fine, later ones
  not — fits a per-request deadline counted from when `fetchAll` starts rather than when each request
  begins, but I could not confirm that. **The lesson is the response, not the diagnosis:** stop
  bisecting an undocumented ceiling and give each request the condition that measured good — alone.
  Chunks now run one per request, sequentially. Corollary worth keeping: `runSQLParallel` is only
  safe for *fast* queries; more than one slow request in a single `fetchAll` is the pattern to avoid.
  Second corollary: when a failure is systematic across a retry, stop treating it as flakiness.
- **Finding (the bug my own verification could not see):** the chunked read failed with
  `Unexpected token 'I', ..."i_margin":Infinity,"... is not valid JSON`. Trino DOUBLE division by
  zero yields **IEEE Infinity, Looker writes it out bare, and `JSON.parse` rejects the whole response
  over one cell.** Cause: the three ROAS confidence-interval expressions divided by `SUM(revenue_d7)`
  with no `NULLIF`, guarded only by customer revenue being non-trivial — over 30 days a creative with
  customer revenue always had revenue too, but inside a 10-day slice it need not. **Chunking exposed a
  latent landmine, it did not create one.**
  The methodological lesson is the bigger one: **`Python`'s `json.loads` accepts `Infinity`;
  JavaScript's `JSON.parse` does not.** Every chunk verification I ran passed because my harness was
  *more permissive than the runtime*. When validating data that another language will parse, assert
  the stricter grammar explicitly — `json.dumps(rows, allow_nan=False)` is the one-line check, and it
  now shows all three chunks clean. **A verification harness that differs from production in what it
  tolerates will certify the bug.**

- **Finding (this is why a timeout looked like "no data"):** **Looker answers a failed SQL Runner
  query with HTTP 200 and an error payload**, not an error status — `{looker_error|message|errors}`
  or `[{looker_error: ...}]`. `JSON.parse` succeeds, so the app stored a "row" and reported 0 rows.
  `runSQLParallel` now sniffs that shape and takes an optional `failedOut` array. The rule that
  forced it: *anything that sums several queries into one number must be able to tell failure from
  emptiness*, or a missing chunk silently understates the total — worse than an error.
