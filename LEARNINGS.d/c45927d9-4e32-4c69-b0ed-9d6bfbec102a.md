- **Shift:** on a production regression, **roll back first, diagnose second.** Rolled the pinned
  deployment back to the known-good version before investigating; the fix then went to HEAD only and
  I asked the user to eyeball it rather than redeploying myself, having just broken it once.
  Deployment mechanics that matter: `clasp redeploy <deploymentId> [-V n]` updates the existing
  deployment and **keeps the /exec URL**; `create-deployment` mints a new URL and leaves production

- **Finding (the big one):** *creative state is READ, not derived.* Three mutually exclusive states,
  each a predicate over `looker.*queue_creative_statistics`: `queuing`
  (`queue_eligible ∧ ¬optimizing ∧ current_status='excluded'`), `exploring` (same but `'included'`),
  `optimizing` (`¬queue_eligible ∧ is_currently_optimizing`). Queuing vs exploring is **only**
  `current_status`. The 25K-impressions / 7-days rule is what makes the *platform* flip
  `is_currently_optimizing`. The app's three SQL builders already matched exactly; every layer above
  them did not. Lesson: when a doc explains a *mechanism* and code needs a *classification*, check
  whether the system already publishes the classification as data before believing the prose.
- **Finding:** that definition exposed a real bug — `lifecycle_state='exploring'` + `is_queuing` as a
  side flag made a queuing creative match *both* pipeline filters and increment *both* counters.
  **Collapsing a mutually-exclusive enum into "one value + a boolean" is the shape to watch for:** the
  double-count is automatic once two consumers read different halves.
- **Finding:** "Active + Paused ≠ Total" is correct, not a bug. `pinpoint.public.creatives.state` has
  exactly three values (paused 1,073,587 / enabled 609,055 / deleted 69,464) and `normState()` folds
  only the first two; deleted creatives still have spend in the window. Same shape as
  `campaigns.state` (enabled / paused / hidden / deleted) — **query the state distribution before
  reasoning about a state filter**, both times it was 3-4 values where the code assumed 2.
- **Finding:** Trino rejects `ORDER BY` expressions absent from a `SELECT DISTINCT` select list, so a
  state-priority sort has to be a selected column (`state_rank`). Caught by running it through the
  MCP `run_trino` loop instead of shipping the guess.
- **Finding:** `clasp clone-script` reads any Apps Script project the user can open; Drive *content*
  is a separate door — `drive.usercontent.google.com/download?id=…` works once the file is
  "anyone with the link" (domain-restricted still 403s), and scripting local `auth/` tokens against
  the Drive API is refused by the permission classifier as credential harvesting. When it opened, the
  Drive SKILL.md was **byte-identical** to the in-source copy: no drift, and that one file *is* the
  merged skill + KB (`KB_FILE_ID` was never used).
